# Requirements Analysis

## 1. Project overview

The Institute of Computing has three computer labs. Teachers currently request lab time through chat messages, which can lead to conflicting bookings. This project prototypes a central reservation interface that displays requests and prevents overlapping reservations.

## 2. Users and roles

### Teacher

- Submit a lab reservation request.
- View, search, and filter reservation records.
- Check the schedule for a selected lab and date.
- Cancel a pending or approved reservation.

### Coordinator

- Review pending reservations.
- Approve or reject a pending reservation.
- Provide a reason when rejecting a reservation.

The current frontend prototype displays coordinator controls without authentication. Role enforcement is a production requirement, not implemented in this browser-only version.

## 3. Lab inventory

| Lab | Maximum students |
| --- | ---: |
| Comlab 1 | 40 |
| Comlab 2 | 30 |
| AES | 25 |

## 4. Reservation information

Each reservation record contains:

- Reservation ID (generated by the application)
- Teacher name
- Lab
- Date
- Start time
- End time
- Purpose
- Number of students
- Status
- Rejection reason, when rejected

## 5. Functional requirements

1. The system shall allow a teacher to submit a reservation with all required reservation information.
2. A new reservation shall have **Pending** status.
3. The system shall reject a student count below one or above the selected lab's capacity.
4. The end time shall be later than the start time, and the date shall not be in the past.
5. A reservation shall be blocked when it overlaps a **Pending** or **Approved** reservation for the same lab and date. The conflict message shall identify the reservation that blocks the request.
6. Reservations in **Rejected** or **Cancelled** status shall not block a time slot.
7. A coordinator shall be able to change a **Pending** reservation to **Approved** or **Rejected**.
8. A rejection shall require a non-empty reason, which shall be retained with the reservation.
9. A teacher shall be able to change a **Pending** or **Approved** reservation to **Cancelled**.
10. A **Rejected** or **Cancelled** reservation shall not be changed again.
11. The system shall provide a schedule for a chosen lab and date. It shall include pending and approved reservations ordered by start time.
12. The system shall allow reservation records to be filtered by teacher name, lab, date, and status.
13. The dashboard shall show total reservation counts for Pending, Approved, Rejected, and Cancelled statuses.
14. Reservation data shall persist in the current browser between page visits.

## 6. Status transition rules

| Current status | Allowed next status |
| --- | --- |
| Pending | Approved, Rejected, Cancelled |
| Approved | Cancelled |
| Rejected | None |
| Cancelled | None |

## 7. Business rules and constraints

- Time conflicts are evaluated only for reservations with Pending or Approved status.
- Two reservations conflict if they use the same lab and date and their time intervals overlap. Back-to-back reservations are allowed.
- Cancelling a reservation releases its time slot because Cancelled reservations are excluded from conflict checks.
- Approval does not bypass the overlap check performed when a reservation is submitted.
- The prototype uses local storage, which is specific to a browser profile and device. It cannot guarantee conflict prevention when multiple devices submit at the same time.

## 8. Non-functional requirements

- The interface should be usable on desktop and mobile screen sizes.
- Form controls should be labelled and validation feedback should be visible.
- User-provided text should be rendered as text, not interpreted as HTML.
- Storage errors should be reported to the user rather than silently treated as a successful save.

## 9. Scope and future work

This project is a front-end prototype. Production deployment would require a shared database and server-side validation, authenticated teacher and coordinator accounts, authorization checks, transaction-safe conflict prevention, and appropriate audit history for status changes.
